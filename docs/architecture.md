# Architecture and boundaries

Place code by responsibility. Target layout:

- `src/types/` — Shared domain types only. Leaf contract layer: zero runtime logic and zero imports from higher layers.
- `src/data/` — Static catalogs (horse names, colors) and demo fixtures used by stories. No runtime logic.
- `src/lib/` — Pure TypeScript domain logic (generation, scheduling, race loop, physics, PRNG). Zero Vue or Pinia imports.
- `src/stores/` — Pinia stores such as `useRaceStore`. Own state transitions, interstitial countdown, and bridge `src/lib/` to the UI.
- `src/composables/` — Reusable Vue and browser-lifecycle logic (`useRaceLoop`, `useSpeedMultiplier`). Flat directory; no domain math or race-state ownership.
- `src/components/` — Presentational Vue 3 SFCs. Pure props-down, events-up. No simulation math.

## Components

One folder per component. Folder names are kebab-case; SFCs keep PascalCase. Tests and stories are co-located with the component they cover.

```
src/components/
  layout/
    app-header/
      AppHeader.vue
      AppHeader.stories.ts
  race/
    auto-advance-bar/
      AutoAdvanceBar.vue
      AutoAdvanceBar.stories.ts
      AutoAdvanceBar.spec.ts
    lane-progress/
      LaneProgress.vue
      LaneProgress.stories.ts
      LaneProgress.spec.ts
  ui/                     # shadcn-vue CLI output — do not restructure
    button/
      Button.vue
      Button.stories.ts
      index.ts
```

Rules:

- **No barrel files** for app-owned components. Do not add or use `index.ts` re-export files; import the SFC directly.
  - Cross-area: `@/components/race/lane-progress/LaneProgress.vue`
  - Same area: `../leaderboard-row/LeaderboardRow.vue` or `./HorseRosterRow.vue`
- Barrels make bundlers traverse unrelated modules and can pull unused components into a chunk. Direct imports keep the graph exact.
- `src/components/ui/**` is generated by the shadcn-vue CLI. Keep its folders and `index.ts` files as generated so CLI updates stay predictable.
- Shared domain types live in `src/types/`, never imported upward from `src/components/`.

Dependency direction:

- `components` may import `composables`, `stores`, `lib`, `data`, and `types`.
- `composables` may import Vue APIs, `stores`, `lib`, `data`, and `types`.
- `stores` may import `data`, `lib`, and `types`.
- `lib` may import `types` only. It must not import Vue, Pinia, stores, composables, data, or components.
- `types` is the leaf layer and must not import from any other layer.

New domain logic goes in `src/lib/` first; wire it into the UI through a store, not directly from a component. Reusable lifecycle logic goes in `src/composables/`; keep it flat.

## Race data flow

```
src/data/horseNames.ts ─┐
src/data/horseColors.ts ─┼─> src/lib/generation.ts ─┐
                        ┘        (pure, injected RNG) │
                                                       ├─> src/stores/race.ts ─> components
src/lib/race.ts ──────────────────────────────────────┘        (phase + derived getters)
        (tick / finish / format)
```

- Generation and simulation are pure and receive `rng`; the store supplies the default.
- The store owns the race phase (`IDLE`/`SCHEDULED`/`RUNNING`/`PAUSED`/`INTERSTITIAL`/`FINISHED`) and all action guards.
- Components derive everything from store getters (`roundViews`, `activeParticipants`, `laneRunners`, `programRounds`); they never re-draw or mutate race data.
- `useRaceLoop` only bridges browser timing to `store.tick`; it owns no race rules.
